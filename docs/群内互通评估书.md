# 群内互通评估书：QQ 群 ↔ 游戏房间

> 文档状态：**仅评估，尚未实现**（写于 0.5.71）
> 适用玩法：海龟汤、谁是卧底、你画我猜（其余玩法可按同一套骨架扩展）
> 读者：后续接手实现的子代理 / 开发者
> 结论先行：技术上可行，海龟汤后端甚至已经预留好 QQ 通道；真正的成本在「群聊噪音控制」和「游戏平衡」这两件产品问题上，不在写代码上。

---

## 1. 一句话结论

现在 QQ 群和房间是**两条单行道**：群只负责建房、发链接、绑定身份、收结算播报；房间内的所有操作都只在网页里发生。
要做「群内互通」，本质是**给群消息加一个路由器**，把「已绑定身份 + 明确命令」的群消息翻译成现有房间动作，再把结果回执到群里。后端动作层大部分可以直接复用，不需要重写游戏逻辑。

## 2. 现状：现在群和房间到底通不通

### 2.1 已经通的（群 → 房间）

| 能力 | 入口 | 说明 |
|---|---|---|
| 建房 | LLM 工具 / `/game 游戏菜单` / 各玩法指令 | 建房后把房间链接发到群里 |
| 查状态 | `花火陪你玩` | 只返回房间列表与配置上限，不注入对局状态 |
| 绑定身份 | `绑定玩家 <8位令牌>`（别名 `绑定令牌`） | 房间页显示一次性令牌 → 群内发送 → `bind_visitor_identity(session_id, token, qq, name)` 把 QQ 绑到某个访客/座位 |
| 撤销绑定 | `/game 撤销网页绑定` | 撤销该 QQ 的全部受信任设备 |
| 加入房间 | 直接发 8 位房间码（`@filter.regex`） | 见 main.py `room_code` 相关正则处理器 |
| 卧底词条录入 | 管理员私聊发多行词条 | 唯一一个用通配正则吃自由文本的先例，可参考它的「状态机 + 超时」写法 |

### 2.2 已经通的（房间 → 群）

- 结算播报：`_send_to_origin` / `_send_to_origin_image`（海龟汤群通报、卧底战报、棋类日报周报）。
- 这些都是一次性推送，不是持续同步。

### 2.3 完全没通的（这才是要做的事）

- 群里的**自由文本不会进房间**：不会变成提问、推理、发言、投票。
- 房间里的对话**不会同步到群**（README 明确承诺：「游戏中的 Bot 回复、系统事件和玩家消息只显示在当前房间 WebUI，不发送到 QQ」）。
- 所以「出题人在群里回一句『是』就能裁决」目前做不到。

### 2.4 已有的隐藏资产（重要，能省很多工）

后端其实已经预留了 QQ 通道，只是没人调用：

| 位置 | 现状 |
|---|---|
| `GameCompanionPlugin.submit_turtle_soup_question(..., source="web"\|"qq", actor_qq="")` | 两个来源都实现了，`source="qq"` 分支按 QQ 找座位 |
| `submit_turtle_soup_answer(...)` | 同上 |
| `RoomManager._require_turtle_soup_player(room, source=..., visitor_token=..., actor_qq=...)` | 有完整的 `source == "qq"` 分支：`seat_for_qq(actor_qq)` → 校验轮次 / 自由提问 |
| `RoomManager.begin_soup_host_judgement(..., source="web"\|"qq", actor_qq="")` | 玩家出题模式下「把问题挂到出题人面前」已支持 QQ 来源 |
| `RoomManager.request_soup_reveal(..., source="qq", actor_qq="")` | 揭晓表决也认 QQ |
| `RoomManager.judge_soup_pending(room, visitor_token, verdict)` | **只认 visitor_token**，要做 QQ 裁决需要补一个 `actor_qq` 分支（小改） |

> 也就是说：海龟汤的「提问 / 推理 / 提示 / 揭晓」四条链路，只要有人把群消息接上去就能跑；只有「出题人裁决」要补几行。

## 3. 目标与非目标

### 目标

1. 群成员**不必打开网页**也能完成对局中的高频操作（提问、回答、发言、投票、猜词）。
2. 群消息的解析必须**零误触发**：绝不能因为群友说了句「是」「不对」就被当裁决。
3. 与网页操作**完全等价**：同一套权限、同一套冷却、同一套胜负判定，不产生第二套规则。
4. 可开关、可灰度：默认关闭，按群/按玩法开启。

### 非目标

- 不做「群聊内容全量同步到房间」——会破坏现有「群聊不注入房间状态」的承诺，也会让房间聊天被群水淹没。
- 不做「群里发图当画板」（你画我猜的画布仍在网页 canvas）。
- 不做跨群房间、不做群内多房间并行（沿用 `rooms.max_group_rooms` 配额）。
- 不做语音、不做图片 OCR 猜词。

## 4. 三个玩法各需要什么（能力矩阵）

| 玩法 | 群内可做 | 群内不可做 | 后端就绪度 |
|---|---|---|---|
| 海龟汤（花火出题） | `问 <问题>`、`答 <推理>`、`提示`、`揭晓` | 看汤面长文（仍建议看网页，群消息只发摘要 + 链接） | **高**：`source="qq"` 全通 |
| 海龟汤（玩家出题） | 同上 + 出题人 `判 是\|否\|无关\|部分`、`判 对\|错` | 填汤面/汤底（长文本，仍在网页表单） | **中**：裁决要补 `actor_qq` 分支 |
| 谁是卧底 | `发言 <内容>`、`投 <号>`、`弃票` | 看自己的词条（隐私！必须私聊或网页） | **中**：接口只吃 visitor_token，桥接层用 `seat_for_qq()` 转换 |
| 你画我猜 | `猜 <答案>` | 画画（canvas）、看画（群内可转发图片，但非必需） | **中**：同上，动作在 `_room_chat_turn` 的 `guess` 分支 |

## 5. 交互设计：群友怎么触发

### 5.1 三种候选触发方式

| 方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| A. 固定前缀命令（`花火 问 ...`） | 零误触发、易解析、易关闭 | 需要记忆命令 | **主方案** |
| B. @机器人 + 关键词（`@花火 问 ...`） | 更显式，不干扰普通聊天 | 手机上多一步 | 与 A 并存 |
| C. 引用回复机器人转发的消息（引用「XX 提问：…」回「是」） | 最自然的裁决方式 | 需要维护「群消息 ID ↔ 待裁决项」映射，平台差异大 | 作为 P4 增强 |

**红线**：不允许「裸关键词」触发（单独一个「是」「否」「投票」不处理）。README 已承诺群聊普通聊天不注入房间状态，破坏这条会被用户投诉。

### 5.2 命令表（建议）

统一前缀可配置，默认 `花火`（也接受 `@机器人`）：

**海龟汤**
```
花火 问 她是不是在等人？          → 提问（等价网页 soup_question）
花火 答 她替去世的丈夫带伞        → 提交推理（soup_answer）
花火 提示                        → 要一条提示（soup_hint）
花火 揭晓                        → 发起揭晓表决 / 出题人直接揭晓
花火 判 是 | 否 | 无关 | 部分     → 出题人裁决（仅玩家出题模式、仅出题人）
花火 判 对 | 错                   → 出题人判定推理
```

**谁是卧底**
```
花火 发言 我觉得这个词和天气有关   → 本轮发言
花火 投 3                        → 投 3 号
花火 弃票
```

**你画我猜**
```
花火 猜 长颈鹿
```

### 5.3 回执策略

- 成功：群内**引用原消息**回一行短句（`已记录，等出题人回答` / `花火：是`），不刷长文。
- 失败：只回给发送者（`@某人 你还没绑定玩家席`），不打扰全群。
- 频控：同一个人 3 秒内只回一次；同一类错误 30 秒内不重复提示。

## 6. 技术方案

### 6.1 新增模块 `group_bridge.py`（建议）

职责单一：**群消息 → 房间动作**，不碰游戏规则。

```python
# 伪代码骨架
@dataclass
class BridgeCommand:
    action: str          # question / answer / hint / reveal / judge / speech / vote / guess
    payload: dict        # {"text": ...} / {"verdict": ...} / {"target": 3}

def parse_bridge_command(text: str, prefix: str) -> BridgeCommand | None:
    """只认明确前缀，解析失败返回 None（= 不接管这条消息）。"""
```

要点：
- 解析器**纯函数**，单独可测，不依赖房间。
- 命令词表放模块常量，方便以后加玩法。
- 解析失败一律返回 `None`，调用方直接 `return`，绝不能「猜意图」。

### 6.2 群消息入口

在 `main.py` 增加一个兜底处理器（参考现有 `undercover_words_add_receive` 的写法）：

```python
@filter.regex(r"^[\s\S]+$")
async def group_bridge_receive(self, event: AstrMessageEvent):
    # 快速短路，避免每条群消息都跑一遍重逻辑
    if not self.group_bridge_enabled:                 # 配置总开关，默认 False
        return
    text = str(event.message_str or "").strip()
    command = parse_bridge_command(text, self.group_bridge_prefix)
    if command is None:
        return                                        # 不是命令，交回普通聊天
    session_id = str(event.unified_msg_origin)
    rooms = self.manager.for_session(session_id)
    if not rooms:
        return                                        # 该会话没有房间，不接管
    ...
```

**必须注意**：
1. 该正则命中所有消息，短路判断要放在最前面（先看开关、再看前缀），避免给每条群消息增加开销。
2. 现有 `undercover_words_add_receive` 也是通配正则，两个处理器会同时被调用；用「前缀不同 + 各自状态机」区分，不要互相消费。
3. 处理成功后可调用 `event.stop_event()`（仓库里已有先例），防止这条消息再被 LLM 回复一遍。

### 6.3 身份解析（关键）

群里发言的人 → 房间里的 visitor：

```
① 按 session_id 找房间：manager.for_session(event.unified_msg_origin)
② 在该房间 visitors 里找 identity_confirmed 且 qq == sender_id 的访客
   → 拿到 visitor.token
③ 若房间是管理员房或多房间并存：报错/要求带房间码消歧，不要猜
```

现有可复用：`room.multiplayer.seat_for_qq(qq)`、`visitor.identity_confirmed`、`visitor.qq`。
未绑定 → 回一句「先在本房间网页里拿令牌，群里发『绑定玩家 XXXX』」，并附房间链接。

### 6.4 动作层：优先复用网页聊天链

**这是本方案最重要的一条**：网页聊天框的自然语言处理已经在 `GameCompanionPlugin._room_chat_turn(room, visitor, cleaned, is_player=..., is_current_player=...)` 里，海龟汤提问/推理/提示/揭晓、你画我猜猜测、卧底发言都在这个函数里分发。

所以桥接层有两条路：

| 方案 | 做法 | 优劣 |
|---|---|---|
| **复用聊天链**（推荐） | `await self._room_chat_turn(room, visitor, "问 xxx", is_player=..., is_current_player=...)` | 一行接通 90% 动作；但返回是给网页的文案，需要裁剪成群消息 |
| 直接调 manager 方法 | `submit_turtle_soup_question(..., source="qq", actor_qq=qq)` | 语义最准、返回结构干净；但要为每个动作单独写分支 |

建议：**海龟汤走方案二**（后端已备好 `source="qq"`，返回结构就是给调用方的），**卧底 / 你画我猜走方案一**（它们只有 visitor_token 接口，走聊天链最省事）。

### 6.5 回执与错误

- 统一 `_bridge_reply(event, text)`：短句、可 @、失败时私聊兜底。
- 异常映射：
  - `PermissionError` → 「你还没绑定玩家席 / 还没轮到你 / 只有出题人能裁决」
  - `ValueError` → 直接回异常文案（现有文案已经面向用户）
  - 其他 → 「这条没处理成功，去网页试一下」+ 日志

### 6.6 去重与限流

- **去重**：AstrBot 事件里取 `event.message_obj.message_id`（若无则用 `sender + text + 秒级时间戳`），保留最近 200 条 LRU，防平台重推导致重复投票。
- **限流**：复用 `RoomManager.CHAT_COOLDOWN_SECONDS`（0.8s）；另加每群 10 条/10 秒的硬上限，超出静默丢弃。
- **单飞**：同一房间同一时刻只处理一条群命令（`room.lock` 已有，动作本身串行）。

### 6.7 房间 → 群 推送（可选，P4）

现状只有结算播报。若要做「局内关键事件也进群」，建议：
- 只推 4 类：轮到谁、谁提问了 + 花火判定、谁被投出、本局结束。
- 合并节流：2 秒窗口内的事件合并成一条，避免一问一答刷屏。
- 默认关闭，配置项 `bridge.push_events`。

## 7. 分阶段实施计划

### P0 基础设施（必须先做）
- 新增 `group_bridge.py`：`BridgeCommand` + `parse_bridge_command()` + 命令词表。
- `main.py` 加兜底处理器 + 总开关 + 前缀配置 + 防重 + 限流 + 统一回执。
- 配置项：`bridge.enabled`（默认 false）、`bridge.prefix`（默认 `花火`）、`bridge.games`（多选：turtle_soup / undercover / draw_guess）。
- 测试：解析器纯函数用例（含「裸关键词不触发」「前缀大小写/空格容错」）、未绑定身份提示、无房间时不接管。

### P1 海龟汤（性价比最高）
- `问 / 答 / 提示 / 揭晓` → 直接调 `submit_turtle_soup_question/answer`、`request_turtle_soup_hint`、`request_soup_reveal`（`source="qq"`）。
- 出题人 `判 是|否|无关|部分|对|错` → 给 `judge_soup_pending` 补 `actor_qq` 分支（或桥接层先用 `seat_for_qq` 换 token 再调，**推荐后者，零改动**）。
- 测试：群里提问能落到 `game.entries`、非出题人裁决被拒、轮次不匹配被拒。

### P2 谁是卧底
- `发言` → `manager.player_undercover_speech(room, seat.visitor_token, content)`。
- `投 N` → `manager.player_undercover_vote(room, seat.visitor_token, N)`。
- 注意：发言内容会进房间公开记录，需确认「群里发言 = 公开发言」的产品语义（卧底发言本来就是公开的，成立）。
- 风险：群里发言会被群友看到，等于把房间发言搬到群，**可能改变游戏节奏**（外置讨论）。建议 P2 先只做「投票」，发言仍留在网页。

### P3 你画我猜
- `猜 <答案>` → `guess`。
- 画布仍在网页，群里只做猜词。
- 建议：猜词结果回执只发「对了/不对」，不重复刷答案。

### P4 增强（视反馈再做）
- 引用回复裁决（维护 message_id → pending 映射）。
- 局内关键事件推送（见 6.7）。
- 私聊通道（词条、身份这类隐私信息走私聊）。

## 8. 改动清单与测试

| 文件 | 改动 | 风险 |
|---|---|---|
| `group_bridge.py`（新增） | 解析器 + 桥接执行 | 低（纯新增） |
| `main.py` | 兜底处理器、配置读取、回执、日志 | 中（通配正则影响所有消息，必须前置短路） |
| `room_manager.py` | 若走「直接调 manager」方案则几乎不改；若补 `judge_soup_pending(actor_qq)` 则小改 | 低 |
| `server.py` | 不改（桥接不经过 HTTP） | 无 |
| `web/*` | 不改（可选：在房间页提示「本群已开启群内操作」） | 低 |
| `_conf_schema.json` | 新增 `bridge` 分组 | 低 |
| `tests/test_group_bridge.py`（新增） | 解析器 + 权限 + 幂等 + 限流 | — |

测试重点：
1. **解析器**：`花火 问 x` 命中；`是`、`花火`、`帮我玩` 不命中；大小写/全角空格容错。
2. **身份**：未绑定 → 明确提示；绑定但不在玩家席 → 提示观众不能操作；绑定且在席 → 落库成功。
3. **权限**：非出题人 `判 是` 被拒；非当前回合 `问` 被拒（与网页一致）。
4. **幂等**：同一 message_id 重复投递只生效一次。
5. **静默**：开关关闭时，任何群消息都不产生回复（回归「群聊不注入游戏」的承诺）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 误触发 | 群友随口一句「是」被判成裁决，直接改变对局 | 强制前缀 + 白名单命令词 + 裸关键词一律不处理 |
| 刷屏 | 一问一答都进群，群变成游戏日志 | 只回执关键结果；事件推送合并节流 + 默认关闭 |
| 隐私泄露 | 卧底词条、身份信息进群 | 词条/身份永不走群；只走私聊或网页 |
| 平衡破坏 | 群里公开讨论让卧底/海龟汤变简单 | P2 先只做投票；发言仍留网页，观察后再放开 |
| 多房间歧义 | 一个群可能有管理员房 + 普通房 | `for_session` 返回多个时要求带房间码，或只认「进行中」的那一个 |
| 平台差异 | aiocqhttp / 其他 adapter 字段不一致 | 只依赖 `unified_msg_origin`、`get_sender_id()`、`message_str` 三个稳定字段 |
| 消息重推 | 重复投票 / 重复提问 | message_id 去重 + 房间动作自身的幂等校验 |
| 与卧底词条录入冲突 | 两个通配正则互相抢消息 | 词条录入只在「管理员私聊 + 待录入状态」生效，桥接只在「有房间 + 命中前缀」生效，交集为空 |

## 10. 验收标准

- [ ] 开关默认关闭时，群内任何消息都不会触发房间动作，也不会产生额外回复。
- [ ] 开启后，已绑定玩家在群里 `花火 问 …`，房间 `game.entries` 出现该提问，网页同步可见。
- [ ] 出题人 `花火 判 是` 生效；其他人群里发同样内容被拒绝且只 @ 他本人。
- [ ] 同一条消息重推不会产生两条记录。
- [ ] 未绑定 QQ 发命令时，收到一次带房间链接的绑定引导，且 30 秒内不重复。
- [ ] 群内操作与网页操作在胜场、统计、复盘、播报上完全一致（走同一套 manager 方法）。
- [ ] 全量回归不新增失败；新增用例覆盖第 8 节 5 类场景。

## 11. 明确不做

- 不做群内画板 / 图片猜词。
- 不做群内长文本录入（汤面、汤底、词库仍走网页或管理台）。
- 不做「@机器人随便说一句话就自动理解成游戏动作」——宁可少做，不可误判。
- 不做群消息全量镜像到房间聊天。
